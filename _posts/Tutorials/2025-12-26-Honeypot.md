I’ve been running a Cowrie SSH honeypot on a Linode instance for about a month now. It started as a small experiment to see what kind of automated noise hits a fresh cloud IP, but it quickly escalated into a massive data-gathering exercise that eventually taught me more about log management and Linux resource limits than actual exploit techniques.

### The Setup
The environment was simple: a standard 1GB RAM Linode instance running Cowrie inside a Docker container. I mapped host port 22 to the container’s port 2222 to catch every bot that assumed it was hitting a real SSH service. For management, I moved my actual SSH access to port 2222.

### The Data Surge
The numbers were way higher than I expected. In just 30 days, the honeypot logged **575,238 attack events** from **2,660 unique IPs**.

Watching the live feed was like watching the heartbeat of the "dirty" internet. Most of it was predictable, but the sheer volume was staggering. Below is a snapshot of the custom dashboard I built to track the chaos in real-time just before the crash.

### The "OOM Killer" Strikes
Everything was fine until the primary log file, `cowrie.json`, crossed the **380MB** mark. My custom Python dashboard backend was written with a "read-it-all" approach, which works great for a few thousand lines but fails miserably at half a million.

The system started lagging, and eventually, the Linux kernel had enough. Because the script tried to load the massive JSON blob entirely into RAM on a 1GB instance, it triggered an **Out of Memory (OOM)** event. I was effectively locked out of the server via SSH and had to use the emergency LISH console to see what had happened.

![Linode LISH console showing the Linux kernel killing the Python process](/assets/Other/OOM.png)
*Figure 2: The emergency console logs showing the OOM killer terminating the memory-hungry Python dashboard processes.*

### The Root Cause Analysis
Why did it fail? It wasn't the honeypot software itself, but the architecture of my monitoring stack. By attempting to load a massive flat file (>380MB) entirely into RAM on a 1GB server instead of streaming it line-by-line, I created a predictable bottleneck that exhausted the server's resources.

### Lessons for V2.0
I ended up deleting the instance to start fresh. Trying to parse massive flat JSON files on a 1GB RAM node in this manner is a losing game. For the next iteration, I’m changing the strategy:

1.  **Stream, don't load:** The Python backend needs to use a `tail -f` style approach or a database like SQLite. Loading the entire log file into RAM is a death sentence for small instances.
2.  **Aggressive Log Rotation:** The active `cowrie.json` file should never be allowed to reach 380MB again. I'll be implementing much stricter rotation policies.
3.  **Better Bind Mounts:** Docker volumes can be a "black box" during a crash. Using direct bind mounts makes it much easier to manage and rotate logs from the host side.

The experiment was a success in terms of data collection, but a valuable failure in terms of operational stability. Time to rebuild.
